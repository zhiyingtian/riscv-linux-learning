## 3. split/merge 画图

```text
分配 order=2，从 order=8 开始：

order 8: [0 ........................ 255]
order 7: [0 ..... 127] + [128 ..... 255] ← 高半挂到 free_area[7]
order 6: [0 ..... 63] + [64 ..... 127] ← 高半挂到 free_area[6]
order 5: [0 ..... 31] + [32 ..... 63] ← 高半挂到 free_area[5]
order 4: [0 ..... 15] + [16 ..... 31] ← 高半挂到 free_area[4]
order 3: [0 ..... 7] + [8 ..... 15] ← 高半挂到 free_area[3]
order 2: [0 ..... 3] + [4 ..... 7] ← 高半挂到 free_area[2]
```

合并路径：

```text
释放 [0..3] 时，buddy 是 [4..7]
第一轮合并后 order = 3
继续合并 [0..7] + [8..15] → order = 4
...
最终合并回 order = 8
```

## 4. 我踩的坑

| 坑 | 现象 | 怎么发现 | 怎么修 |
|---|---|---|---|
| 合并时 buddy 的地址低于 page | free 时合并循环不收敛，甚至死循环 | 合并后 page 没有指向低地址块 | 合并后把 page 指向低地址块，并同步更新 order |
| buddy 与 page 的 order 不同时，page 没有挂回当前 order 的 free_area | merge 循环不前进，order 一直不变化 | while 循环里观察 order | 停止 merge，把 page 挂回当前 order 的 free_area，并更新 nr_free |
| 未对齐 page 被当作块头释放 | free_count 被错误增加，`buddy_check()` 失败 | 用 `p+1` 伪造 order-1 块头做测试 | `buddy_free()` 增加 `(page - pages) & ((1UL << order) - 1)` 检查 |

## 6. 和 Linux 对照

| tiny-mm | Linux 5.15 | 对应关系 |
|---|---|---|
| `struct free_area` | `include/linux/mmzone.h:97` | Linux 每个 order 有 `free_list[MIGRATE_TYPES]` 和 `nr_free`；tiny 先简化为单个 `head` |
| `__rmqueue_smallest()` | `mm/page_alloc.c:2448` | 从目标 order 向上找第一个非空 free_area；对应 `buddy_alloc()` 的向上查找 |
| `expand()` | `mm/page_alloc.c:2289` | 把大块 split 到目标 order，高半挂到低一级 free_area；对应 split 循环 |
| `__free_one_page()` | `mm/page_alloc.c:1058` | 释放页并尝试 merge；对应 `buddy_free()` |
| `__find_buddy_pfn()` | `mm/internal.h:178` | `buddy_pfn = pfn ^ (1UL << order)`；tiny 用页数组下标做 XOR |
| `page_is_buddy()` | `mm/page_alloc.c:891` | 检查 buddy 是否同 order 且处于空闲状态；对应 `buddy->order == order && buddy->is_free` |

## 7. 还没懂的问题

1. `free_area` 当前不按地址高低排序；这对正确性没影响，但对分配路径的缓存局部性和合并行为有什么影响？Linux 是否也不强制排序？
2. `struct page` 里只有 `buddy_next`，没有 `buddy_prev`；摘除 buddy 需要扫描链表。Linux 的 `struct page` 用 `struct list_head lru` 双向链表，空间和时间上如何权衡？

## 8. 进入 M3 前的一句话总结

> buddy 的本质是：把物理页按 `2^order` 分块，用 `free_area[order]` 的空闲链表管理这些块；分配时向上找块并 split，释放时找 buddy 并 merge，从而保证分配出的块连续且按 order 对齐。
